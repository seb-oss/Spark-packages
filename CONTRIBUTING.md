# Contributing

## Releasing packages

This repo uses [Changesets](https://github.com/changesets/changesets) for versioning and changelogs. Releases are fully automatic and need no release PR: every push to `main` runs all checks (including e2e) once, then `release.yml` versions the packages, pushes the version commit to `main` and publishes to npm via trusted publishing.

### Existing packages

1. Add a changeset: `yarn changeset`
2. Commit and push to `main` (or merge a PR). The pre-push hook runs `yarn smoketest`.
3. CI checks, versions and publishes. No manual step.

If publishing fails after the version commit was pushed, fix the cause and run `gh workflow run release.yml`. It publishes every version missing from npm. Re-running the failed run does not, because its commit is no longer the tip of `main`.

### Automated updates

- **Dependabot** PRs merge themselves once every check, including e2e, passes. Public packages whose `dependencies`, `peerDependencies` or `optionalDependencies` changed get a patch changeset, committed to `main` right after the merge; devDependency, GitHub Actions and Docker updates merge without a release.
- **ISO packages** (`iso-10383`, `iso-4217`) are regenerated weekly from their published sources by `iso.yml`. Changes are committed with a minor changeset to a branch, checked, fast-forwarded onto `main` and released.

### Dependencies

- Exact versions everywhere except `peerDependencies`, which use ranges.
- New npm versions are blocked for 3 days (`npmMinimalAgeGate` in `.yarnrc.yml`, `cooldown` in Dependabot).

### Code checks

- `yarn lint` runs Biome in every package and applies safe fixes; it still fails on errors it cannot fix. `yarn lint:ci` only checks, fails on warnings too, and also rejects imports from `dist/`; `yarn smoketest` and CI run it. The `no-type-assertion` plugin (`biome/no-type-assertion.grit`) makes `x as T` an error; only `as const` is allowed. Use type guards or stricter types. Where an assertion is inherent (a trust boundary), keep it with `// biome-ignore lint/plugin/no-type-assertion: <reason>`. `noFloatingPromises` makes a promise that is neither awaited nor handled an error, because its rejection would be unhandled and end the process; mark one that cannot reject with `void` and a comment saying why.
- `yarn typecheck` runs `tsc --noEmit -p .` and then `vitest --typecheck.only` in every package.
- Inside the repo, types of other `@sebspark/*` packages come from their source, so the editor jumps to the code and nothing needs building first. Every export names its source first, under the `@sebspark/source` condition (`"@sebspark/source": "./src/index.ts"`), and every package's `tsconfig.json` turns it on with `customConditions`. Installs from npm are unaffected: they don't set the condition, and `src` isn't published. TypeScript skips a condition whose file is missing, so even a consumer that sets it gets `dist`. `tools/source-types.test.mjs` enforces this, and `yarn generate:package` sets it up.
- Every `vitest` call in a package script passes `--fsModuleCachePath node_modules/.vitest-cache`. Without it, all packages share the workspace root's cache, and parallel runs clear it at the same time after a lockfile change (`ENOTEMPTY`). `tools/vitest-cache-per-package.test.mjs` enforces this.
- `yarn test:tools` runs the repo's own tests (`tools/*.test.mjs`) twice: as is, and with `FORCE_COLOR=1`. CI and agents run without a terminal, where tools print no colours, so a test that breaks on colour codes would otherwise pass there and fail only for someone at a terminal.
- Generated code is gitignored and generated by the `test` and `typecheck` scripts that need it. Yarn 4 does not run `pre`/`post` scripts.

### CI

- Actions are pinned by commit SHA (Dependabot keeps them current). Every workflow declares its `GITHUB_TOKEN` permissions, read-only by default, and each job asks only for what it needs.
- Automation never opens or updates PRs with `GITHUB_TOKEN`: GitHub holds the checks of such PRs for approval, and nobody approves them. It pushes branches and runs checks with `workflow_call` instead.
- Pushes and merges made with `GITHUB_TOKEN` don't trigger workflows, so automation dispatches `release.yml` itself.
- Turbo's cache is kept between runs with `actions/cache`.

### Repository protection

- Everyone with write access is trusted and may push straight to `main`. The `main` ruleset only blocks deleting it and force-pushing to it.
- Workflow runs from outside contributors always need approval by a maintainer.

### New packages

The release pipeline publishes with npm trusted publishing (OIDC), which only works for a package that already exists on npm and trusts `release.yml`. So a new package is published once by hand, and then trusts the pipeline, before its first release is pushed to `main`. `tools/check-first-publish.mjs` enforces the first part: it runs in `yarn smoketest` (so also before every push to `main`) and before versioning in `release.yml`, and fails when a public package is not on npm yet. `changeset publish` would try to publish every such package, changeset or not.

You need npm CLI 11.15 or later (the repo's Node version has it), 2FA on your npm account, and write access to the `@sebspark` organisation. Run everything from the repo root, with the new package committed but not yet pushed:

1. **Log in:** `npm login`. Check it with `npm whoami`.
2. **Build:** `yarn build`.
3. **Publish each new package by hand**, at its current version (`0.0.0`). If one new package depends on another, publish the dependency first.
   ```bash
   (cd packages/<package-name> && npm publish --access public)
   ```
   npm asks for 2FA, either a one-time code or a link to open in the browser. Run these steps in an interactive terminal: without one (e.g. from a script or an agent's shell), npm exits with `EOTP` instead of waiting for you.

   A new package takes a few minutes to appear: npm accepts the publish (HTTP 202 in the debug log) and processes it first, so `npm view` answers 404 for a while. npm also lists a `<version>-stage` version, which it creates during that processing. The warning that npm "auto-corrected some errors in your package.json" only means it normalised `repository.url` to `git+https://`; it is harmless.
4. **Let the package trust the pipeline.** `--allow-publish` is required: without it, npm only allows `npm stage publish`, and the pipeline's publish fails.
   ```bash
   npm trust github @sebspark/<package-name> --file release.yml --repo seb-oss/Spark-packages --allow-publish --yes
   npm trust list @sebspark/<package-name>
   ```
   When setting up several packages, choose "skip two-factor authentication for the next 5 minutes" on the first 2FA prompt, and wait 2 seconds between packages to avoid rate limiting. `npm trust list` asks for 2FA too. The same can be done on npmjs.com, under the package's Settings, then Trusted publishing.
5. **Push `main` within 2 days.** A trusted publisher that has not published within 2 days of being created expires; delete it with `npm trust revoke --id <id> @sebspark/<package-name>` and create it again.
6. **Check the release:** the `release.yml` run publishes the version from the changeset (e.g. `0.1.0`). Confirm with `npm view @sebspark/<package-name> versions`.

npm requires the manual first publish to prevent name squatting under organisation scopes.
